## Intent

**Problem:** The app has no backend yet — no Supabase clients, no schema, no way for `super_admin`/`employer` to authenticate or for `/painel-8f2k/*` to be protected. Every later epic (leads, cases, financeiro) depends on this foundation.

**Approach:** Ship the full Supabase schema (all 8 tables + `current_role()` + RLS + the two triggers described in doc 08) as `supabase/setup.sql` plus a matching first entry in `supabase/migrations/` (see file convention below) — per doc 08's own suggested implementation order, this avoids fragmented migrations once later epics add FKs across tables. Wire up Supabase clients (browser, server, service-role), a `proxy.ts` (this Next.js version renamed `middleware.ts`) enforcing session + role on `/painel-8f2k/*`, and a minimal login flow + protected `/painel-8f2k/leads` stub so the auth loop is testable end-to-end. Only Epic 1's app-layer logic (auth) ships this round; leads/cases/financeiro app code comes in later specs.

**Supabase file convention (human-specified 2026-09-24, applies to every future epic, not just this one):**
- `supabase/setup.sql` — the full base schema, hand-maintained, run once against a fresh Supabase project.
- `supabase/migrations/NNNN_description.sql` — one file per incremental schema change going forward, numbered sequentially. This spec's schema work is migration `0001`.
- `supabase/migrations.sql` — generated, never hand-edited. A script concatenates every file in `supabase/migrations/` (in filename order) into this single file, so it can be pasted into the Supabase SQL editor in one shot.

## Boundaries & Constraints

**Always:**
- Follow doc 08 schema verbatim (column names/types/checks) for all 8 tables, `current_role()` (`SECURITY DEFINER`), and RLS policies.
- Never hand-edit `supabase/migrations.sql` — it's regenerated by the migrations script; edit `supabase/setup.sql` or add a new numbered file under `supabase/migrations/` instead.
- Service-role client only ever imported in server-only files (route handlers, server actions) — never reachable from a Client Component bundle.
- `proxy.ts` (not `middleware.ts` — deprecated in this Next.js version) does two checks per doc 08: no session → redirect to `/painel-8f2k/login`; session but wrong role for the route → redirect to `/painel-8f2k/leads`.
- Login uses a Server Action calling `supabase.auth.signInWithPassword`, matching this Next.js version's recommended auth pattern (form + Server Action, no client-side fetch).
- A user authenticated in Supabase Auth but absent from `admin_users` is treated as unauthorized, per FR1 AC3.

**Never:**
- No Epic 2+ app code (leads UI/API, cases, financeiro) in this spec — only the shared schema for those tables.
- No public sign-up screen.
- No styling polish on the login/leads-stub pages — functional only, plain semantic HTML, no Tailwind classes; visual design is explicitly deferred to a later front-end pass (confirmed with the human 2026-09-24).

## Implementation Notes

- **Critical fix, found in orchestrator verification, not by the implementing subagent:** doc 08's `current_role()` (and the subagent's identical implementation) does not run. `current_role` is a PostgreSQL reserved keyword (synonym for `current_user`); `CREATE FUNCTION current_role()` is accepted, but calling it with parentheses — `current_role()`, exactly how every RLS policy in the migration used it — is a syntax error, including inside `CREATE POLICY`. Verified against a real Postgres 16 (disposable Docker container): bare `current_role()` fails with `ERROR: syntax error at or near "("`; renaming to `app_current_role()` and re-running the full `setup.sql` end-to-end (with stub `auth`/`storage` schemas) succeeds, and both triggers (`mudanca_status`, `last_interaction_at`) verified functionally correct with real inserts/updates. Renamed the function to `app_current_role()` everywhere: `supabase/setup.sql`, `supabase/migrations/0001_initial_schema.sql`, regenerated `supabase/migrations.sql` via `pnpm db:migrations` (never hand-edited), and doc 08 itself (with an inline note explaining why), since doc 08 is the schema's source of truth and must stay accurate for later epics. No app code referenced `current_role()` (Epic 2+ territory), so nothing else needed updating.
- `.env.example` created ahead of the rest of the implementation, at the human's request, with the 3 Supabase vars and inline usage notes (which are public vs. server-only-secret). `.gitignore` updated with `!.env.example` so it stays committed despite the blanket `.env*` ignore rule.
- Doc 08's "Modelo de dados" section defines 7 tables (`leads`, `lead_interactions`, `lead_meetings`, `cases`, `admin_users`, `projects`, `financial_transactions`), not 8 as this spec's Approach/Tasks text says. Implemented all 7 documented tables verbatim; treating the "8" as an off-by-one in the spec's own prose rather than a missing table, since no 8th table is described anywhere in doc 08.
- `proxy.ts` filed as `src/proxy.ts`, not a root-level `proxy.ts` — the app directory lives at `src/app`, and Next's convention is "project root, or inside `src` if applicable, so that it is located at the same level as `pages` or `app`."
- Storage bucket `case-images` (public read / `super_admin` write) is included in `supabase/setup.sql` and migration `0001`, even though no epic ships Storage upload code yet — it sits inside doc 08's RLS section (lines 151-164) that the Code Map explicitly scopes in for this spec.
- Added `server-only` as a direct dependency (not previously in `package.json`) — required for the `import "server-only"` guard in `src/lib/supabase/admin.ts` and `src/lib/auth/get-current-admin.ts`; it was only a transitive dependency of Next.js before, which doesn't satisfy a direct top-level import.
- `src/lib/supabase/database.types.ts`'s `Database` type adds an empty `Relationships: []` per table and empty `Views`/`Functions` maps beyond what doc 08 specifies — required by `@supabase/supabase-js`'s `GenericTable`/`GenericSchema` constraints for `createClient<Database>()` to type-check; without them the generic silently resolved to `never` and all `.from(...)` calls lost their types.
- `proxy.ts` and the login flow only check `admin_users` membership via a live `select` inside the request, per the doc's model (no session-embedded role). This adds a Supabase round trip per protected-route request; acceptable for the current traffic profile, but worth revisiting if `/painel-8f2k/*` traffic grows enough to matter.
